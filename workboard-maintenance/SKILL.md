# Worklens

**Turn scattered updates into clear project context.**

An agent skill for evidence-backed progress, decisions, and next actions.

Maintain a concise, evidence-backed view of current work without turning the
source archive into the interface. This skill records the existing Workboard
contract; do not impose its UI conventions on unrelated products.

## Start with the requested scope

1. Read the applicable memory and workspace instructions. Locate the existing
   board and read its README and relevant content/refresh rules. Do not initialize
   a second board or assume a personal path, project list, account or schedule.
2. Briefly discuss the approach before edits. Distinguish content curation,
   source refresh, UI maintenance and portable packaging. Permission for one
   does not authorize the others.
3. Before any content curation or source refresh, read
   [Progress and relevance](references/progress-and-relevance.md).
   When deriving tasks or preparing their next handoff, read
   [Work rounds and handoffs](references/work-handoffs.md).
   Before UI/status/resource changes, also read
   [Presentation contract](references/presentation-contract.md).
   Before saving or sharing anything, read
   [Safe changes](references/safe-changes.md).

## Non-negotiable content boundaries

- **Progress is highlights, not transcripts.** Show consequential change,
  conclusion or material exploration under a short English title, with its
  real date and necessary direct citations. Do not force Stage/Phase.
- **Board-editing instructions are not project developments.** Never display a
  cleanup conversation as Progress or turn the user's rejected examples into
  pending decisions. Direct project confirmations can support concise facts.
- **Old communication is not current work.** Reconcile completion, supersession
  and project scope before carrying anything forward. Unread evidence is a
  coverage gap, not proof of an unfinished action.
- **Observed behavior is not automatically a bug.** Separate current fact,
  proposal, judgment, decision and implementation. Do not create a fix task
  without an actual request or established defect.
- **Preserve evidence without replaying it.** Keep stable IDs, original records,
  personal state and history; do not render old chats/open-question lists inside
  expanded Progress. Removing irrelevant copy is not completing a task.
- **Use one current interpretation across views.** Product memory and Ongoing
  share the same highlights and status resolver. A full history versus the latest
  three highlights is a display-depth difference, not a factual contradiction.
- **One work record, several entrances.** To-do and project Next steps share
  stable action IDs and personal state. Small requests and complex work rounds
  qualify when ownership, current action and a bounded finish are evidenced.
  Preparation neither creates duplicate tasks nor hides the user's turn. FYI is
  not an assignment. Preserve the approved handoff structure: current action,
  what happened, prepared output and user judgment. Curate its contents rather
  than deleting the format or reverting concrete actions to broad old titles.
  Actual preparation can be summarized and linked; chapter outlines/discussion
  logs are not assignments. Direct user commitments from Codex may be evidence;
  assistant suggestions are not commitments.

## Save gate

For each affected project, inspect the actual rendered summary **and expanded
content**, not only headings or screenshots of collapsed cards:

- Does each highlight answer what materially changed, with scope and evidence?
- Is every current dependency specific, relevant and still unresolved?
- Are rejected examples, completed follow-ups, raw excerpts and unrelated
  project discussions absent from the reading projection?
- Do Ongoing, Product memory and affected tasks agree without inventing approval,
  shipment, ownership, deadlines or metrics?
- Are original evidence and personal changes preserved, and are source dates/
  coverage ledgers unchanged for editorial-only work?

For an all-project request, review every project, including legacy/review-backed
records; changing one renderer or one example is not an all-project content pass.
Use the regression cases in the content reference for relevant changes.

## Record corrections

Update the relevant rule here or in its linked reference, not a growing duplicate
changelog. Mark superseded guidance explicitly in the board's local rules so it
cannot override the current contract on a later refresh. Keep project-specific
facts and user identities in private project memory, never in this portable skill.
Report what was actually checked; a skill reduces recurrence, not guarantees it.
